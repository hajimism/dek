# dek

**台本から組み立てる HTML スライド。** — *Talk-script-first HTML slides.*

`dek` はトークスクリプトを起点にスライドを組み立てる CLI です。台本を Markdown で書き、その見出しひとつひとつが 1 枚の HTML スライドになります。テーマと規約はプロジェクトで共有し、発表のたびにデッキを足していく。AI エージェントと一緒に作ることを前提に設計されています。

> *dek* は *deck* の異綴りです。`deck` は Kong の decK が使っているため一文字落としています。導入前に `command -v dek` で `PATH` の衝突だけ確認してください。

---

## Why

**スライドは喋るための資料です。** ところが PowerPoint も Google Slides も Slidev も、まず箱を置き、あとから中身を考える順序で作られています。その結果、立派だが本番で喋り切れない資料ができあがる。本来の順序は逆です。何を喋るか → その瞬間に画面に何が出ているべきか。`dek` は `script.md` を親に据え、スライドはそこから生やします。

**トークは一度きりではありません。** 発表のたびに新しいリポジトリを切ると、見た目も規約も毎回ゼロから積み直すことになります。`dek` はプロジェクトを一度作り、その中にデッキを溜めていきます。規約はプロジェクトのもの、見た目は前回の続きから、台本とスライドはデッキごと。過去のデッキがそのまま次の出発点になります。

**AI と作るなら、ファイルは小さく分かれているべきです。** 3,000 行の `slides.md` の 7 枚目だけを直す、というタスクは LLM にとって不必要に難しい。1 スライド = 1 HTML なら、編集対象は 40 行のファイルがひとつ。差分が読め、壊れてもその 1 枚で済みます。

**AI は自分が書いた HTML がどう見えるか知りません。** 文字が枠からはみ出していても、テキストとして出力された HTML は完璧に見える。人間が本番 30 分前に気づきます。`dek` は描画結果を機械可読な診断として返し、AI が自分で確認して直すループを回せるようにします。

## 設計の三原則



### 1. `script.md` が順序と台本の単一の真実

デッキの**順序**と**トークスクリプト**は `script.md` だけが持ちます。スライド HTML は各セクションに従属します。親子関係を構造で固定することで、片方だけが更新されて食い違う事態を防ぎます。

`slides/` のファイル名は slug のみで、連番を持ちません。順序を持つファイルは `script.md` ひとつです。スライド内で要素が現れる順序も同じで、HTML は `script.md` のビートを番号で指すだけです。

### 2. スライドは単体で開ける完結した HTML

各 `slides/*.html` は `<html>` から始まる完全なドキュメントで、`<link rel="stylesheet" href="../theme.css">` を自分で書きます。

```
open decks/2026-04-vite/slides/architecture.html
```

ビルドを通さずブラウザで確認でき、スクリーンショットも撮れ、AI にファイルを 1 つ渡せば文脈が完結します。build 時は `<body>` の中身だけを抜き出して結合します。

同じ性質をデッキ全体にも広げます。**デッキディレクトリは外を参照しません。** `theme.css` も画像もその中にあり、ディレクトリごとコピーしても、zip で誰かに送っても、5 年後に開いても同じように描画されます。プロジェクトはデッキを置く場所であって、デッキが依存する実行環境ではありません。

### 3. 規約は lint で担保する

「使える CSS クラスはこれだけ」「デッキの外を参照しない」といった規約は、ドキュメントに書くだけでは守られません（人間も AI も）。すべて lint ルールとして実装し、SARIF で出力します。

`lint` **が通ることが「完成」の定義です。** そして開発サーバは保存のたびに lint を走らせるので、普通に作業していれば常に通っている状態が保たれます。

## Quick Start

プロジェクトを作るのは最初の一度だけです。最初のデッキも一緒に作れます。

```bash
dek init my-talks --deck 2026-04-vite
cd my-talks/decks/2026-04-vite
```

あとは 3 手です。

```bash
$EDITOR script.md   # ① 喋ることを書く（ここに一番時間をかける）
dek                 # ② 開発サーバ。見出しからスライドが生え、保存のたびに描画と lint が走る
dek build           # ③ ../../dist/2026-04-vite.html — この 1 ファイルで発表できる
```

同梱のデフォルトテーマでそのまま喋れます。見た目に手を入れるのは、何度目かのデッキで十分です。

### コマンド

日常的に使うのは 2 つです。


| コマンド        | 役割                                  |
| ----------- | ----------------------------------- |
| `dek`       | 開発サーバ。sync・HMR・lint・プレゼンタービューをすべて内包 |
| `dek build` | 単一 HTML へ結合（アセット全インライン、プレゼンタービュー内蔵） |


プロジェクトとデッキの管理。


| コマンド                                   | 役割                                      |
| -------------------------------------- | --------------------------------------- |
| `dek init [dir] [--deck <name>]`       | プロジェクトを作る（省略時はカレント）                     |
| `dek new <name> [--theme-from <deck>]` | プロジェクトにデッキを追加                           |
| `dek ls [deck]`                        | デッキ一覧、またはデッキ 1 つの概要（枚数・lint 状態・セクション一覧） |
| `dek pdf`                              | PDF 出力                                  |


1 枚を扱うもの。人間も AI エージェントも、この粒度で作業します。


| コマンド                                    | 役割                           |
| --------------------------------------- | ---------------------------- |
| `dek show <slug>`                       | 台本と HTML をまとめて出す             |
| `dek check <slug> [--shot]`             | その 1 枚を lint し、描画結果を確認する     |
| `dek shot [slug] [--step k]`            | スクリーンショット出力（既定は全要素表示の最終ステップ） |
| `dek mv <slug> --before|--after <slug>` | セクションの並べ替え                   |
| `dek goto <slug>` / `dek current`       | 開いているブラウザを飛ばす／今表示している枚を知る    |


CI やスクリプトから個別に呼ぶためのもの。開発サーバが内部で使っているものと同じ実装です。


| コマンド                                           | 役割                                           |
| ---------------------------------------------- | -------------------------------------------- |
| `dek sync`                                     | `script.md` → 空スライド HTML の生成、`AGENTS.md` の更新 |
| `dek lint [--fix] [--visual] [--format sarif]` | 検証                                           |
| `dek help --agent`                             | 全コマンドの使い方を 1 画面に圧縮して出す                       |


すべてのコマンドが `--json` を受け付けます。人間向けはテキスト、機械向けは JSON か SARIF。`init` と `sync` は**既存ファイルを絶対に上書きしません**。足りないものを作り、余ったものを警告するだけです。

### 実行場所がスコープを決める


| どこで実行したか             | 対象      |
| -------------------- | ------- |
| プロジェクト直下             | 全デッキ    |
| デッキの中                | そのデッキ   |
| どこでも `--deck <name>` | 指定したデッキ |


`dek.toml` を上へ探索してプロジェクトルートを決めます（Cargo workspace と同じ）。プロジェクト外で `dek new` を叩くと `dek init` を促して終了します。

## ディレクトリ構造

```
my-talks/                       # ← プロジェクト（dek init）
├── dek.toml                    # lint 閾値
├── theme.css                   # 新しいデッキの出発点（テンプレート）
├── AGENTS.md                   # AI 向け規約（sync が自動生成）
├── assets/                     # 素材の置き場。デッキへはコピーして使う
├── decks/
│   ├── 2026-04-vite/           # ← デッキ（dek new）
│   │   ├── script.md           #    単一の真実
│   │   ├── theme.css           #    作成時にコピーされた、このデッキのもの
│   │   ├── slides/
│   │   │   ├── intro.html
│   │   │   └── architecture.html
│   │   └── assets/             #    このデッキが実際に使う素材
│   └── 2026-09-dek/
├── .dek/
│   └── schema.json             # script.md の JSON Schema（自動生成）
└── dist/
    └── 2026-04-vite.html       # build 成果物（単一ファイル）
```

**デッキが 1 つだけでも** `decks/` **は必ずあります。** どのプロジェクトも同じ形をしているので、CLI も開発サーバも AI エージェントも、パス解決に分岐を持たずに済みます。

### テーマは複製する

プロジェクト直下の `theme.css` は**新しいデッキの出発点**です。`dek new` はこれをデッキの中へそのままコピーします。

```
theme.css  ──[dek new がコピー]──>  decks/2026-09-dek/theme.css
```

コピーである理由は、**デッキが過去のイベントのスナップショットだから**です。共有参照にすると、9 月にテーマを磨いた結果として 4 月に喋ったデッキの描画が変わり、見出しが 1 行に収まらなくなり、lint が過去のデッキに対して警告を出しはじめる。**終わったトークは終わった状態で固定されるべきで、それには物理的なコピーがいちばん確実です。**

得られるものもあります。

- スライド HTML は常に `<link rel="stylesheet" href="../theme.css">`。プロジェクト構造が変わっても不変。
- lint がクラス語彙を解決するとき、読むファイルは 1 つ。
- デッキディレクトリをそのままコピーすれば、別の場所でも動く。

編集の向きは常に一方向です。

```bash
dek new 2026-09-dek                               # プロジェクトの theme.css から始める
dek new 2026-09-dek --theme-from 2026-04-vite     # 過去のデッキから始める

cp decks/2026-09-dek/theme.css theme.css          # 今回の改良を次回の出発点にする
```

最後の行は `cp` そのものなので専用コマンドを持ちません。**過去のデッキが、そのままテーマのライブラリになります。**

`assets/` も同じ扱いです。プロジェクト直下は素材の置き場で、デッキは使うものを自分の `assets/` へコピーします。プロジェクト側からロゴを消しても、去年のデッキは壊れません。

## `script.md`

覚えるルールは 2 つです。`## 見出し` **が 1 スライド**、その配下に書いたものが台本。台本は普通の Markdown で、何を書いてもかまいません。

```markdown
---
# yaml-language-server: $schema=../../.dek/schema.json
title: HTML スライドツールを作った話
event: Tokyo Frontend Meetup #42
date: 2026-04-18
---

## intro

こんにちは。今日は、スライドツールを自分で作った話をします。

> 自己紹介は短く。時計を見ない。

## problem

みなさん、発表の前日に何をしていますか。

聴衆が「自分ごと」だと思うまで喋る。3 つ目が本命。

## architecture

さて、ここが今日いちばん覚えて帰ってほしいところです。
左が入力、右が出力。

### script.md が親

まず script.md がいて、

### スライドがぶら下がる

その下にスライドがぶら下がっている。逆ではありません。

### 逆だと喋れない

この向きが逆だと、資料が立派になるほど喋れなくなります。
```

プレゼンタービューはセクションの Markdown をそのまま描画します。ディレクションを台本と見分けたければ blockquote を使う、程度の習慣で足ります。専用の記法はありません。

### `###` はビート

`##` が 1 枚なら、`###` はその中の**ビート**です。喋りの区切りであり、画面が次の段階へ進む瞬間でもあります。

本番で矢印キーを押すと、まずビートが進み、ビートを使い切ると次のスライドへ移ります。プレゼンタービューは今喋っているビートを台本上でハイライトします。スライド HTML は各ビートに `data-step` で要素を対応づけますが（後述）、対応する要素のないビートがあってもかまいません。画面はそのまま、喋りだけが進む区切りとして使えます。

「いつ出すか」は喋りの決定なので `script.md` が持ち、「どう出すか」は見せ方なので `theme.css` が持つ。この分担が、段階表示を台本先行のまま実現します。

### ルール

- `## 見出し` **= 1 スライド**。並び順がそのままスライド順。
- 見出しテキストが **slug** になり、`slides/<slug>.html` に対応。`[a-z0-9-]+` のみ。
- `### 見出し` **= ビート**。テキストは自由（プレゼンタービューの見出しになる）。並び順がステップ番号。
- 見た目に関する情報は `script.md` に置きません。レイアウトも装飾も、スライド HTML 側の責務です。

`event` と `date` は `dek ls` の表示に使われ、タイトルスライドから参照できます。

### スキーマ

Zod で定義し、そこから JSON Schema を生成します。1 箇所の定義がランタイム検証とエディタ補完の両方に効きます。

```ts
const Beat = z.object({
  title: z.string(),
  body: z.string(),            // ビート配下の Markdown
  line: z.number(),
});

const Section = z.object({
  slug: z.string().regex(/^[a-z0-9-]+$/),
  body: z.string(),            // 最初のビートまでの Markdown
  beats: z.array(Beat),        // beats[k-1] が data-step="k" に対応
  line: z.number(),            // 診断の位置情報用
});

const Deck = z.object({
  title: z.string(),
  event: z.string().optional(),
  date: z.string().date().optional(),
  ratio: z.enum(["16:9", "4:3"]).default("16:9"),
  sections: z.array(Section).min(1),
});
```

`.dek/schema.json` をプロジェクト直下に `sync` のたびに書き出し、frontmatter 冒頭の `$schema` コメントで VS Code の YAML 拡張に食わせます。

lint 閾値とテーマの既定はプロジェクトの `dek.toml`、デッキ固有の値は frontmatter。設定ファイルはこの 2 つだけです。

## スライド HTML

```html
<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <link rel="stylesheet" href="../theme.css">
</head>
<body>
  <section class="slide" data-layout="two-col">
    <h2 class="slide-title">script.md が親</h2>
    <div class="col">
      <p class="node">script.md</p>
      <p class="node node-parent" data-step="1">script.md ← 親</p>
    </div>
    <div class="col" data-step="2">
      <p class="node">intro.html</p>
      <p class="node">architecture.html</p>
    </div>
  </section>
</body>
</html>
```

- ルートは `<section class="slide">` ひとつ。slug はファイル名から決まり、`data-slug` は build が注入します。
- 書き方は自由です。終了タグを閉じても省略しても、属性に引用符を付けても付けなくても、正しい HTML5 であれば受け付けます。minify は build が一括で行います。
- レイアウトは `data-layout` で選ぶ。既定テーマは `title` / `default` / `two-col` / `full-bleed` / `quote` を持ちます。
- 論理サイズは **1280 × 720 固定**。表示側で `transform: scale()` してビューポートに合わせます。
- **CSS はテーマのクラス語彙のみ**。スライド内の `<style>` と `style=` は lint で禁止。
- **JS はスライドに置きません。** 動きはすべてランタイムと `theme.css` が担います。
- テーマのセレクタは必ず `.slide` 配下にスコープすること。トップレベルセレクタはプレゼンター UI を汚染します。



### 段階表示: `data-step`

`data-step="k"` を持つ要素は、`script.md` の k 番目のビートで現れます。ランタイムがやるのは、現在のステップ以下の要素に `is-shown` を付けることだけ。**どう現れるかは** `theme.css` **が決めます。**

```css
/* theme.css */
.slide [data-step] { opacity: 0; transform: translateY(8px); transition: .3s; }
.slide [data-step].is-shown { opacity: 1; transform: none; }
```

フェードでもスライドインでも、テーマを書く人の判断です。アニメーションの記法は CSS そのもので、dek が語彙を足すことはありません。

既定テーマは `opacity` と `transform` で隠します。`display: none` を使わないのは、レイアウトがステップによって動かないようにするためです。これで `lint --visual` のはみ出し判定がどのステップでも同じ結果になります。

### トランジション: View Transitions

スライド間の遷移はブラウザ標準の View Transitions API を使います。ランタイムは `document.startViewTransition()` を呼ぶだけで、動きはテーマが書きます。

```css
/* theme.css */
::view-transition-old(root) { animation: fade-out .2s; }
::view-transition-new(root) { animation: fade-in  .2s; }
```

要素を**次の枚へ連れていく**こともできます。

```html
<!-- problem.html -->
<img class="figure" data-morph="pipeline" src="assets/pipeline.svg">

<!-- architecture.html -->
<img class="figure figure-small" data-morph="pipeline" src="assets/pipeline.svg">
```

ランタイムが `data-morph` を `view-transition-name` に変換し、ブラウザが 2 枚の間で位置とサイズを補間します。図が右上に小さく退いて次の話が始まる、という表現が属性 1 つで書け、スライドは単体で開ける完結した HTML のままです。

既定テーマは `prefers-reduced-motion` を尊重し、指定があればすべての動きを省きます。

### 密度はテーマが決める

1 枚にどれだけ載せられるかは、`theme.css` のフォントサイズと余白が決めます。文字を大きく取っておけば、詰め込んだ瞬間に枠からはみ出し、`lint --visual` が客観的に鳴る。閾値を数で決める代わりに、**幾何で真偽が決まるルール**に密度の管理を委ねています。詰め込みたければテーマの文字を小さくする、という一手が、意図的な設計判断として差分に残ります。

## 開発サーバ

`dek` はデッキの中で叩けばそのデッキを、プロジェクト直下で叩けばデッキ一覧をインデックスとして出します。

保存のたびに、次のことが起きます。

- `script.md` **を保存** — 新しい見出しに対応する空スライドを生成し、対応のなくなった HTML をブラウザに警告表示する
- `slides/*.html` **を保存** — HMR で該当スライドを再描画し、lint を走らせ、診断をブラウザのオーバーレイと端末の両方に出す
- `theme.css` **を保存** — 全スライドを再描画し、クラス語彙を再解決する
- Playwright があれば、描画系のルール（はみ出し・コントラスト）も保存ごとに評価する

明示的に `sync` や `lint` を叩く必要はありません。普通に編集していれば、常に lint が通る状態に保たれます。

### プレゼンタービュー

`/presenter` を開くと、現在のスライド、次のスライド、そのセクションの台本が並び、今喋っているビートがハイライトされます。送るとまずビートが進み、使い切ると次のスライドへ。WebSocket 経由で接続中の全インスタンス（別ウィンドウ、別デバイス、スマホ）が追従します。

`dek goto <slug>` と `dek current` は、この同期に別プロセスから参加するためのコマンドです。開発サーバが立っている間、端末から（つまり AI エージェントから）人間のブラウザを動かし、人間が今見ている枚を知ることができます。

## Lint



### 責務の分担


| 層            | 担当               | 例                                               |
| ------------ | ---------------- | ----------------------------------------------- |
| Markdown の作法 | **rumdl**（外部）    | 見出しレベル飛び、行長、リンク切れ                               |
| スキーマ         | 自作（Zod）          | frontmatter、slug 形式                             |
| 整合性          | 自作               | `script.md` ↔ `slides/*.html`、ビート ↔ `data-step` |
| テーマ準拠        | 自作（HTMLRewriter） | 未定義クラス、インライン `<style>`                          |
| 自己完結         | 自作               | 外部参照、デッキ外参照                                     |
| 描画           | 自作（Playwright）   | はみ出し、コントラスト                                     |


一般的な Markdown のルールは `rumdl` に完全に委譲します。自作するのは `rumdl` が原理的に見られない**ドメイン固有のルールだけ**です。

### ルール


| ID       | 内容                                           | fix |
| -------- | -------------------------------------------- | --- |
| `DEK001` | `script.md` にあるが `slides/` に HTML がない        | ✅   |
| `DEK002` | `slides/` にあるが `script.md` に対応セクションがない       | —   |
| `DEK003` | `data-step` に対応する `###` ビートが `script.md` にない | —   |
| `DEK004` | `data-step` が 1 から連続していない                    | —   |
| `DEK005` | 同一スライド内で `data-morph` の名前が重複                 | —   |
| `DEK010` | テーマに定義のないクラスを使用                              | —   |
| `DEK011` | スライド内に `<style>` / `style=` 属性 / `<script>`  | —   |
| `DEK012` | テーマにトップレベルセレクタ                               | —   |
| `DEK013` | `theme.css` のクラス数が上限を超過（既定 40）               | —   |
| `DEK020` | 外部 URL（CDN・リモート画像）の参照                        | —   |
| `DEK021` | 参照している画像ファイルが存在しない                           | —   |
| `DEK022` | デッキディレクトリの外を参照している（`../../assets/` など）       | —   |
| `DEK030` | 描画時に内容がスライド枠外へはみ出す。全ステップで評価（`--visual`）      | —   |
| `DEK031` | コントラスト比が 4.5:1 未満（`--visual`）                | —   |


`DEK020` / `DEK021` / `DEK022` はまとめて**デッキの自己完結**を守るルールです。リモートも、プロジェクト直下も、隣のデッキも、デッキの中からは参照できません。`build` が全アセットをインライン化できるのは、この制約があるからです。

`DEK010` **の限界について** — このルールは `theme.css` にクラスを足せば回避できます。意図的にそうしています。語彙を増やすのは設計判断であって、lint が禁じるべきものではない。lint が担うのは、それを**一手の摩擦と、レビュー可能な差分として可視化する**ことだけです。`DEK013` は、その一手が無限に繰り返されないための上限です。

クラスが増えるのはデッキの `theme.css` の中だけなので、他のデッキには波及しません。気に入った語彙だけを、あとから `cp` でプロジェクトの `theme.css` に引き上げます。

### 出力

診断はすべて **SARIF 2.1.0** に統一します。

```bash
dek lint --format sarif > results.sarif
```

`rumdl --output-format sarif` の `runs[]` とマージするため、VS Code、CI、AI エージェントがすべて同じ形式を読みます。人間向けには ESLint 風のテキスト出力が既定です。

> **なぜ SARIF か** — 「lint が通るまで直して」というループを AI に回させるには、診断が機械可読である必要があります。テキスト出力のパースは壊れます。

## 本番

```bash
dek build   # dist/2026-04-vite.html
```

成果物は全アセットをインライン化し、minify した単一の HTML です。会場では**このファイルだけ**をブラウザで開きます。

build がやることは 4 つです。

1. 各スライドの `<section class="slide">` を抽出し、`data-slug` を付けて結合する。タグ間の空白を落とす
2. `theme.css` を minify する
3. `assets/` の画像を data URI にする
4. ランタイム JS を minify して埋め込む

外部の HTML minifier は使いません。入力の形は問わず、出力は常に同じ形になります。

`?presenter` を付けて開くとプレゼンタービューになり、同じブラウザで開いた別ウィンドウが `BroadcastChannel` で追従します。外部モニタに本体、手元にプレゼンター、という構成が、サーバもネットワークも要らずに成立します。

スマホをリモコンにしたいなど、別デバイスからの操作が必要なときだけ開発サーバを使います。

```bash
dek --remote   # LAN に公開。プレゼンター画面はパスワード保護
```

USB メモリに 1 ファイル入れておけば必ず発表できる、という状態を最優先に設計しています。

## アーキテクチャ

```
                 ┌─────────────────┐
                 │   core (parser) │   project → Deck[]
                 │   + rules       │   Deck + slides/ → Diagnostic[]
                 └────────┬────────┘
                  ┌───────┴───────┐
                  │               │
             ┌────┴────┐    ┌─────┴─────┐
             │   CLI   │    │ dev server│
             └────┬────┘    └─────┬─────┘
                  └──── HTTP ─────┘   goto / current / check
```

**core を独立モジュールとして切り出す**のが設計上の要点です。CLI と開発サーバが同じパーサ、同じルールセット、同じプロジェクト解決を共有します。パーサが 2 箇所にあると必ず挙動がズレます。

CLI は開発サーバが立っていればそれに HTTP で問い合わせ、立っていなければ自分で core を呼びます。`goto` と `current` のようにブラウザの状態を扱うコマンドだけが、開発サーバを必須とします。

### エージェントとの接点は CLI

AI エージェントは、人間と同じ CLI を使います。専用のプロトコルもツール定義もありません。

コーディングエージェントはシェルとファイル編集を既に持っています。スライドは 1 枚 40 行の HTML なので、エージェント自身の編集ツールで直接書くのがいちばん正確で、いちばん安い。並べ替えのように壊れやすい操作だけ `dek mv` として用意します。

CLI が使われるツールになるために、次の 4 つを守ります。

- **すべてのコマンドに** `--json`**。** 診断は SARIF。テキストをパースさせる出力を作りません。
- **エラーは次の一手を言う。** 「`slides/intro.html` がありません。`dek sync` で生成できます」のように、そのまま実行できる文で失敗します。
- `dek help --agent`**。** 全コマンドの使い方を数百トークンに圧縮して出す。CLI 自身が自分のリファレンスです。
- `AGENTS.md` **は短く保つ。** `sync` が生成する内容は、三原則、規約、テーマのクラス語彙、`dek help --agent` へのポインタ。数十行で収め、詳細は必要なときに CLI から引かせます。

これで `AGENTS.md` を読むエージェントなら、Claude Code でも Codex でも OpenCode でも、追加設定なしに dek を扱えます。

### 一往復で直す

```bash
dek check architecture --shot
```

`check` はその 1 枚だけを lint し（Playwright があれば描画系のルールも含む）、スクリーンショットを書き出し、SARIF と画像のパスを返します。エージェントは HTML を書き、`check` を叩き、返ってきた画像を自分の目で見て直す。**書いた → 見た → 直した**が一往復で閉じます。検証と確認が別々の呼び出しだと、その分だけループが遅く、途中で確認を省く誘惑が生まれます。

### 指差しは双方向

`dek goto <slug>` と `dek current` は対になっています。エージェントが編集した直後に人間の画面を該当スライドへ飛ばし、人間が画面を見ながら「この枚、右の図を小さくして」と言えば、エージェントは `dek current` で slug を知り、聞き返さずに直せる。**指差しが双方向に通る**ことが、協働の体験を決めます。

### 描画のフィードバック

**幾何で確定判定できるものは、すべて lint ルールにします。** はみ出しもコントラストも、Playwright で測れば真偽が決まる。スクリーンショットを見せて「はみ出ていますか」と尋ねるより、はるかに精度が高い。

- `lint --visual` — AI が自分の出力を検証するための一次手段。SARIF を返す。
- `shot` — 判定ではなく観察のため。デザインの良し悪しと最終確認は人間に残す。

## 技術選定



### Bun

1. `HTMLRewriter` **が組み込み。** Cloudflare の lol-html ベース。クラス抽出も build 時の `<body>` 抽出も、依存ゼロ・Rust 速度で書けます。
2. `bun build --compile` **で単一バイナリ。** クロスコンパイル対応。`deno compile` より成果物が大幅に小さい。
3. **HTML ファイル群をエントリとして扱える。** ネイティブのトランスパイラとバンドラ、HMR が組み込み。

3 については留保があります。`bun './slides/*.html'` は各ファイルを**独立したエントリ**として扱いますが、実際に必要なのは全スライドを 1 つのビューに載せてキー送りできる画面です。合成層（親フレーム + HMR 中継）は自前で書くことになります。Vite プラグインより薄いものですが、ゼロではありません。

**代償:** Playwright は Bun の部分的な Node 互換性の影響を受けます。`--visual` / `shot` / `pdf` は Playwright を別プロセスで起動し、依存はオプショナルかつ動的 import とします。単一バイナリ配布時は同梱せず、未検出なら該当機能だけが「`bunx playwright install` してください」と言って失敗します。**CLI 全体はいかなる場合も起動できること。**

### rumdl（Markdown lint）

Rust 製、markdownlint のドロップイン代替。markdownlint の 53 ルール + 独自 31 ルールで計 84。LSP 内蔵、`--watch` あり、`sarif` を含む出力形式が後方互換を保証されています。Firefox、Docker Docs、Apache Lucene、PyO3 などが採用。

プラグイン機構を持たないため、ドメイン固有ルールは `dek` 側に置きます。この分業は構造的に必然です。

### Zod v4

`z.toJSONSchema()` でスキーマ定義から JSON Schema を生成できます。Standard Schema 準拠なので周辺ツールにロックインされません。ArkType は速いが DSL の学習コストが乗り、Valibot のバンドルサイズ最適化は CLI では効きません。

### 採用しなかったもの


| 候補                   | 理由                                              |
| -------------------- | ----------------------------------------------- |
| **Node.js**          | HTMLRewriter 相当が実用的に存在しない                       |
| **Deno**             | HTMLRewriter がなく、Playwright まわりで詰まりやすく、バイナリが大きい |
| **Vite 8**           | Rolldown 化で十分速いが、依存を 1 つ減らしたい                   |
| **Biome**            | Markdown 対応は入ったが、ルール数で rumdl に及ばない              |
| **remark / unified** | 台本は `##` で区切るだけなので、mdast は過剰                    |

## Slidev との違い

**[Slidev](https://sli.dev)** は同じ領域の最も成熟した実装であり、設計の多くを参考にしています。プレゼンター同期、Playwright のオプショナル化、CSS のスコープ規約はいずれも Slidev の解法を踏襲しています。

決定的に違うのは**ファイル分割、台本の位置づけ、そして単位**です。


|            | Slidev                      | dek                               |
| ---------- | --------------------------- | --------------------------------- |
| プロジェクトの単位  | 1 リポジトリ = 1 デッキ             | 1 プロジェクト = N デッキ                  |
| スライドの実体    | 単一 `slides.md`（`src:` で分割可） | 1 スライド = 1 HTML                   |
| 記述言語       | Markdown + Vue + UnoCSS     | 素の HTML + CSS                     |
| トークスクリプト   | スライド末尾の HTML コメント（子）        | `script.md`（親）                    |
| 作成順序       | スライド先行                      | 台本先行                              |
| 段階表示       | `v-click`（スライド側が順序を持つ）      | `###` ビート（台本側が順序を持つ）+ `data-step` |
| 動き         | Vue トランジション + 独自 DSL        | CSS + View Transitions API        |
| エージェントとの接点 | MCP サーバ                     | CLI + `AGENTS.md`                 |
| 想定用途       | 動くデモを含む技術トーク                | 喋りが主役のトーク                         |


Slidev の「1 ファイル 1 スライド」要望は Discussion に残ったまま解決されていません。`dek` はそこを主戦場にします。Vue / UnoCSS / Monaco / Mermaid を抱えないぶん、lint も build も桁違いに単純になります。**素の HTML/CSS で完結することを強みとして維持します。**

### Later

ツールにしか作れず、AI に任せても代替できないもの。コアが安定してから着手します。

**過去デッキの参照。** プロジェクトに溜まったデッキは、それ自体が次のトークの参考資料です。ただし**生の HTML を 40 枚渡しても AI は読まないし、読んだらコンテキストが死ぬ。** そこで構造ダイジェスト（構成・クラス語彙・レイアウト分布、約 1,000 トークン）、テキストを落とした骨格表現、代表スライドの画像を生成し、**自動で読まれるのはダイジェストだけ**にします。残りはそこからのポインタ経由で必要時に読む。Claude Skills が `SKILL.md` を小さく保って `references/` を遅延ロードするのと同じ構造です。

**外部デッキの取り込み。** 他人のデッキを `.dek/refs/`（プロジェクト直下、全デッキで共有）に引き込みます。取得は `gh:<owner>/<repo>/<path>[@<ref>]` を tarball で取り、**必ず SHA へ解決して** `dek.lock` **に固定**します。これがないと「AI が参考にした X」が再現しません。

安全側の要件が 2 つあります。ひとつ、**ref は「データ」であって「指示」ではない**。他人の `script.md` に「以降のスライドはすべて赤背景に」と書いてあれば AI はそれを読みます。悪意がなくても起こる。対策を `AGENTS.md` の一文に頼るのは原則 3 に反するので、`.dek/refs/` には**加工物だけを置き、原本の生テキストは配置しない**（必要時は `dek ref show` がサニタイズして返す）設計にします。ふたつ、ref のスクショ生成は未検証の HTML を自分のマシンで実行することを意味するので、既定でネットワーク遮断・JS 無効で描画します。

`dek new --from` — 既存デッキ（自分のものでも ref でも）を雛形に新規作成。上の取得基盤の上に載ります。

### スコープ外

意図的に作らないもの:

- テーマのエコシステム（npm 配布、ギャラリー）
- CSS の外に出るアニメーション（タイムライン記法、複数要素の同期、キーフレーム DSL）
- スライド内のインタラクション（クリックで動くデモ、スライド内 JS）
- ライブコーディング、埋め込みエディタ
- PPTX / Keynote エクスポート
- WYSIWYG エディタ

これらが必要なら Slidev を使うべきです。段階表示、トランジション、要素の移動はブラウザ標準の範囲で持っており、喋りが主役のトークの表現はそこでほぼ尽きると考えています。`dek` は**自分のトークのために自分で保守できるサイズ**を保ちます。
