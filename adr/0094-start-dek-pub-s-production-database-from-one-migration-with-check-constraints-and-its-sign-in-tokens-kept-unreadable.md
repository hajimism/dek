# 94. Start dek.pub's production database from one migration, with CHECK constraints and its sign-in tokens kept unreadable

Date: 2026-11-15

## Status

Accepted

## Context

The first `void deploy` on 2026-11-15 created the production D1, `dek-pub-db`, and applied the 13 migrations in `apps/pub/db/migrations/`. It then stopped before uploading the Worker, because R2 was not yet enabled on the account. The database held the tables and no rows.

Those 13 files record how the schema was reached during development, not what production needs:

- `threads`, `replies` and `public_comments` were made with `guest_name` and then rebuilt without it (ADR 61).
- `grants.side` was added defaulting to `client`, then rebuilt to default to `guest` (ADR 64).
- `decks` was rebuilt only to change the default of `visibility`.
- Two of them update or delete rows, which only a development database had (ADR 64: "A development database keeps its grants").
- The rebuilds open with `PRAGMA foreign_keys=OFF`, which does nothing on D1, where foreign keys are always enforced.

Wrangler records the names of applied migrations in `d1_migrations`. A squashed file would count as pending on the database that ran the 13 and fail on its existing tables. Squashing is therefore cheap only before the database holds rows.

A survey of the schema before the first rows found three more things that cost a table rebuild, or a rewrite of every row, once accounts exist:

- **Types held only in TypeScript.** `decks.visibility` and `comments`, `threads.scope`, and `grants.role` and `side` are Drizzle `enum` columns, and `decks.script_public` and `embed` are `boolean` mode. None of it reaches the SQL, so a row written by hand, or by a query that skips the types, can hold any value. A grant could also name neither an account nor an address. In SQLite a CHECK constraint can only be added by rebuilding the table.
- **Lookups with no index.** `claimGrants` runs on every new session and finds grants by `user_id`, and by `email` where `user_id` is null, across all decks. The check for a waiting grant on sign-in finds them by `email`. Both unique indexes on `grants` lead with `deck_id`, so these queries scanned the table. `deleteDeck` deletes `mutes` by `deck_id`, which their key, led by `user_id`, cannot find. An index can be added at any time; it is added here because the migration is being remade anyway.
- **Tokens stored in plain text.** Better Auth keeps GitHub's access, refresh and ID tokens in `account` as they came, and the magic-link plugin keeps each sign-in link's token in `verification.value` as it was mailed. dek.pub never uses GitHub's tokens after sign-in. Whoever reads a copy of the database, from a backup, Time Travel or an export, could use a GitHub token, or sign in with a link not yet used. Changing this after accounts exist would leave earlier rows in plain text.

## Decision

**Production starts from one migration, generated by `void db generate` from `db/schema.ts` and `auth.ts`.** The 13 files and their snapshots are removed. The production D1 that ran them is deleted and made again by `void deploy`, and `void.lock.json` takes the new database's id. This is done once, while the database is empty. From here on, migrations are only ever added, as ADR 43 has it.

**The schema states its rules in SQL.**

- CHECK constraints hold each `enum` column to its values, and each `boolean` column to 0 or 1. The values are written once in `db/schema.ts` and used for both the column's type and its constraint.
- `grants_names_someone` requires a grant to name an account or an address.
- Indexes `grants_user`, `grants_email` and `mutes_deck` serve the lookups above.

**Sign-in tokens are kept unreadable.**

- `account.encryptOAuthTokens` is on, so GitHub's tokens are encrypted with `BETTER_AUTH_SECRET`.
- The magic-link plugin keeps a link's token hashed (`storeToken: "hashed"`).

**Foreign keys stay out, as ADR 82 decided.** One of ADR 82's reasons is wrong: D1 does not need `PRAGMA foreign_keys` for each connection, since it always enforces them. Its other reason now matters more. A Drizzle table rebuild drops the old table, and on D1 that deletes the children of an `ON DELETE CASCADE` key. Whether keys without CASCADE are worth having is left to a decision of its own.

**Not changed:**

- Timestamps stay ISO-8601 text in dek.pub's tables and integer milliseconds in Better Auth's. No query joins the two.
- Names stay snake_case in dek.pub's tables and camelCase in Better Auth's.
- Addresses and handles stay lowercased by the code, not by `COLLATE NOCASE`.

## Consequences

- The migration history before 2026-11-15 is in git only. A local database made before this change no longer matches the migrations. It is deleted and made again: the dev server's state directory, or Miniflare's.
- A query that writes a value outside an enum, or a grant with neither key, fails in the database instead of storing it.
- Rotating `BETTER_AUTH_SECRET` makes the stored GitHub tokens unreadable. dek.pub never reads them, so nothing breaks.
- A sign-in link's token cannot be read back from the database, and nothing in dek.pub needs to.
- The next schema change is an ordinary added migration. Squashing again would mean another empty database, which production will not have again.
