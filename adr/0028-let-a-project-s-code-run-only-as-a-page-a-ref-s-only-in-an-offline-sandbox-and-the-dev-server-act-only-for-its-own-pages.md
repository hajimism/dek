# 28. Let a project's code run only as a page, a ref's only in an offline sandbox, and the dev server act only for its own pages

Date: 2026-10-27

## Status

Accepted

Amended by [29. Say whenever Chromium draws without its sandbox, and draw a ref so only with DEK_ALLOW_UNSANDBOXED](0029-say-whenever-chromium-draws-without-its-sandbox-and-draw-a-ref-so-only-with-dek-allow-unsandboxed.md)

## Context

dek has made its security decisions one at a time, each where a report or a review found a hole: reads and writes kept inside the project (242f218); `DEK_` variables and the GitHub token taken only from what the user sets (7f4629b, 62c896b, da02b7c, [ADR 12](0012-take-github-tokens-and-dek-variables-only-from-what-the-user-sets.md)); no `bunfig.toml` or `tsconfig.json` of the project's reaching dek's own process (0418909, 3eed8f0); Chromium's sandbox and no network for the pages dek draws (550cc3a); refs and packs read as someone else's decks ([ADR 15](0015-hand-a-deck-over-as-a-pack-and-read-it-as-a-ref.md), [ADR 17](0017-start-a-deck-from-a-ref-s-theme.md)); the dev server's Host and Origin checks and its presenter password; and dependency code kept away from the tokens that publish ([ADR 19](0019-keep-dependency-code-away-from-the-tokens-that-publish.md)).

No record says who dek trusts and what each of them may make it do. Each change has had to work that out again, and the next ones need it written down to be argued against: what dek does where Chromium's sandbox cannot start, and how text from a ref reaches the user's agent. The first of them, the headers the dev server sends, lands with this record.

This record is written from the code it lands on, with the headers part 4 adds, and from runs against both on 2026-10-27. Where the code falls short of what a part below says, the shortfall is listed under Open items, not left out.

## Decision

The user who runs `dekc` is trusted, and so is the environment they start it in: the arguments they type, `PATH`, the `DEK_` variables that choose the programs dek runs, and `GITHUB_TOKEN` or `GH_TOKEN`. Everyone else is trusted with what follows, and no more.

**1. The deck author**: whoever wrote the project's decks, the user or the author of a project the user cloned.

- **Controls**: `script.md`, `theme.css`, the `.html`, `.css`, and `.ts` files in `slides/`, `assets/`, `voice.toml`, and `dek.toml`, and so the pages built from them.
- **dek guarantees**: their slide scripts run as page code and never in dek's own process: a slide script that imports is refused before Bun's transpiler reads it, lint checking the rest of it with every import blanked out, and Bun compiles one that imports nothing without running any of it. When dek draws a page itself (`shot`, `lint --visual`, `check`, `pdf`, `pptx`, `video`, `dekc --visual`, and `build` for its cover picture when the deck has a `url`), it is in Chromium with its sandbox on where it starts (part 7) and the network off. When the user opens the dev server or a build, it is in the user's browser, with what that browser allows; in the dev server a slide script has the server's origin, so on every page of a local server, and on the presenter's pages under `--remote`, it can do what the presenter can. To check `motion`, lint evaluates a script's top-level code in a separate bun, in a `node:vm` context with no host objects and a timeout; that keeps a broken script from stopping lint and is not a sandbox. A project's files cannot make dek read or write outside it: for every file of a project that dek reads or writes, `dek.toml`, `theme.css`, and the voice files included, it follows a link only to a file of the same kind inside the project and outside hidden folders, and it follows `decks/` only to a folder there. dek's own writes of a project's files go through `safe-fs.ts`, to a fresh file renamed into place, with four exceptions: `build` copies its cover picture with `copyFileSync`, to a path `outputPath` checked first; the files `dekc init` and `dekc new` start a project or a deck with are written once with `wx`, which writes through nothing already there; a ref's snapshot is written into a fresh folder under `refs/` and swapped in whole (part 2); and Chromium and ffmpeg write their own files. The engine `voice.toml` names receives the script's text: the project's own words, sent where the project says.
- **Enforced in**: `src/core/slide-script.ts` (`transpiler`, `loadSlideScripts`, `compileSlideScript`), `src/core/slide-script-eval.ts` and `src/core/slide-eval-worker.ts`, `src/core/playwright.ts` (`launchChromium`), `src/core/playwright-visual.ts` (`runVisualRequest`, `offline: true`), `src/video/worker.ts`, `src/core/safe-fs.ts` (`followInside`, `readSourceIfExists`, `writeInside`, `outputPath`, `removeInside`), `src/core/resolve.ts` (`readDeckFile`, `resolveProject`), `src/core/assets.ts` (`fileInside`), `src/core/build.ts` (the cover picture), `src/cli/files.ts` (`applyPlan`).
- **Shown by**: `tests/core/safe-fs.test.ts`, `tests/core/slide-script.test.ts` ("a slide script that imports is refused before Bun reads it", "a slide script that imports is still checked for the rest"), `tests/core/config.test.ts` ("refuses a dek.toml that links out of the project"), `tests/core/resolve.test.ts` ("a decks folder that is a link"), `tests/core/playwright-browser.test.ts` ("draws with the network off"), and `tests/server/dev.test.ts` ("refuses an asset symlink that leads out of the deck", "serves no voice file that links out of the project").

**2. A ref's or a pack's author**: someone else, whose deck the user pinned in `[refs]` to read as a model.

- **Controls**: every file in their repository or pack and every folder and file name in it, and so the deck's title, slugs, text, theme, slide scripts, and assets. Not the pin, which files a snapshot keeps, or where it is written.
- **dek guarantees, on fetching**: a GitHub tarball is at most 200 MB, downloaded within ten minutes, and gunzipped through a count that stops at 1 GB; a pack is at most 50 MB, gunzipped through a count that stops at 100 MB. dek reads either tar with its own reader ([ADR 27](0027-read-a-pack-s-or-a-repository-s-tar-with-dek-s-own-reader-so-nothing-unpacks-beyond-what-was-counted.md)): each file is a copy of the bytes the tar stores for it, so nothing comes out larger than what was counted, folders and links are left out, and a tar that holds anything else, such as a sparse file or a device, or more entries than it may, is refused before any file is made. dek drops the first segment of every tar entry's path unchecked, as the tarball's top folder, then drops the entry when its path starts with `/`, holds a backslash, or has an empty, `.`, or `..` segment in what is left, so `../x/y` is kept as `x/y`. A snapshot keeps the project's `dek.toml`, the deck's `script.md`, `theme.css`, `slides/`, and `assets/`, and a license, 50 MB at most, written beside the old one and swapped in, never through a link under `refs/`; a pack's copy in `packs/` is written and removed only as a plain file, never through a link there. The pin is a commit or a sha256 of the kept files, and a pack that does not match it is not unpacked.
- **dek guarantees, on reading**: `ls`, `show`, `theme`, and `shot` read a ref, and `new --theme-from` copies its `theme.css` with a first line that names the ref and a warning when it has no license; from then on that theme is the new deck's own. Every other command that takes a deck, the dev server included, refuses a ref by name, and no command, the dev server and `dekc init` included, runs in a directory inside one: a folder is a ref only as dek writes one, a `dek.toml` beside the marker that names the ref, at that ref's own place under a project's `refs/`. `shot` keeps a ref's shots in the reading project's `.cache/refs/`, so nothing dek does writes in a snapshot once `dekc ref` wrote it. A ref is not linted (`ls` says lint was skipped), built, or served by the dev server. Its slide scripts are read as part 1 says, one that imports refused before Bun's transpiler reads it, and run only in `shot`, in Chromium with its sandbox on where it starts and the network off: in a run on 2026-10-27, `fetch`, a WebSocket, an image, `sendBeacon`, and WebRTC's STUN from a page drawn that way reached nothing, and with the network on, all of them did.
- **dek guarantees, on what reaches the agent**: `show`, `theme`, `ls`, and `ref` print a ref's text as it is, and `--json` marks it with `ref`, its name, rev, snapshot, and license. AGENTS.md lists each ref as a read-only model, with its title on one line of at most 80 characters, so the title cannot start a heading or an instruction there. Text for a terminal shows every control character other than a color code, a line break, or a tab as U+FFFD. dek does not keep a ref's words from asking the agent to do something: what `show` prints is what the agent was asked to learn from, and what it does with it is the agent's judgment.
- **Enforced in**: `src/core/ref.ts` (`readTarball`, `readPack`, `pickSnapshot`, `snapshotDigest`, `writeSnapshot`, `refuseLinkUnderRefs`, `refuseLinkUnderPacks`, `requireProject`, `refuseInsideRef`), `src/core/tar.ts` (`readTar`), `src/core/github.ts` (`downloadTarball`), `src/core/ref-name.ts`, `src/cli/ref.ts` (`addPack`, `unpackSnapshot`), `src/cli/scope.ts` (`resolveScope`, `resolveTarget`), `src/cli/init.ts`, `src/server/dev.ts` (`startDevServer`), `src/core/shot-cache.ts`, `src/cli/main.ts` (`run`), `src/cli/ls.ts`, `src/cli/new.ts` (`provenance`), `src/core/sync.ts` (`refTitleLine`), `src/cli/tty.ts` (`terminalSafe`), and the parts named in 1 for Chromium.
- **Shown by**: `tests/core/ref.test.ts` (paths that could escape, a pack or a tarball that inflates past the limit, the digest, a link under `refs/`), `tests/core/tar.test.ts`, `tests/core/pack.test.ts`, `tests/cli/pack.test.ts` ("a pack's slide script", "a link at packs/"), `tests/cli/ref.test.ts` ("keeps a ref's title to one line of AGENTS.md, however it is written"), `tests/cli/ref-read.test.ts` ("every command takes a ref name as its deck, so resolveScope refuses it", "a directory inside a ref is not a project to run commands in", "init makes no project inside a ref", "a marker above an ordinary project makes no ref of it", "ls times the ref at its own speaking rate and says lint was skipped"), `tests/server/dev.test.ts` ("refuses to start inside a ref, and writes nothing there"), and `tests/cli/tty.test.ts` (`terminalSafe`).

**3. The audience of `dekc --remote`**, and of `dekc rehearse --remote`: anyone who can reach the machine over the network.

- **Controls**: the requests they send to the server's addresses, and a phone that scans a pairing code.
- **dek guarantees**: the server listens on `0.0.0.0` only with `--remote`, and on `127.0.0.1` otherwise. With `--remote`, dek makes a password on each start, 10 letters or 50 bits, never one the user chooses. A request to any route is cleared for the presenter by HTTP Basic with that password, by `?token=` with it, or by the cookie a pairing code leaves, each compared in constant time. The presenter page adds the token to its socket, event stream, marks, and annotations, since a socket and an event stream cannot send headers. A pairing code is 16 letters or 80 bits, works once and within five minutes, and becomes an HttpOnly, SameSite=Lax cookie for 12 hours; the redirect drops the code from the address, and the cookie's secret is new on each start, so a restart ends every pairing. `ROUTE_EXPOSURE` gives the audience the deck list, the player without notes, the slides, the theme, the deck's `assets/` (every file in it, hidden ones and ones no slide uses included, each only where it lies inside the project, as part 1 says of every read), the event stream with only its sync and reload events (`EVENT_EXPOSURE`), and a socket that hears where the deck is and where the laser points, and whose own messages are dropped. Everything made from the script is the presenter's: the presenter view and its notes, the voice timeline and audio, `current` and `goto`, marks, annotations, and diagnostics. A server started for one deck serves no other. The password is kept in `.dek/server.json`, mode 0600, for `dekc goto` and `dekc current`.
- **What a presenter may do**, with the password or a paired phone: read all of the above, move the deck, point the laser, and mark beats and add, edit, remove, clear, or restore annotations, which dek writes to `.dek/marks.json` and `.dek/annotations.json`. An annotation is the presenter's words, which `dekc annotations` later hands to the user's agent ([ADR 7](0007-keep-annotations-in-dek-and-let-agents-list-them-with-dekc-annotations.md)): dek limits who writes it, not what it says.
- **Enforced in**: `src/server/dev.ts` (`accessFor`, `answer`, `roomSockets`), `src/server/auth.ts` (`clearance`, `ROUTE_EXPOSURE`, `EVENT_EXPOSURE`, `mayRead`, `pairingResponse`), `src/server/pairing.ts`, `src/server/lan.ts` (`generateRemotePassword`), `src/server/routes.ts` (`routeRequest`, `sseResponse`, `safeDeckAsset`), `src/server/pages.ts` (`includeNotes`, `liveToken`), `src/runtime/routes.ts` (`splitDeckPath`), `src/server/lock.ts`.
- **Shown by**: `tests/server/auth.test.ts` ("clearance"; "exposure", which pins every presenter route, the annotations and diagnostics events, and on the audience's side only the player and `reload-slide`), `tests/server/pairing.test.ts`, `tests/server/routes.test.ts` ("a server scoped to one deck serves its routes at the root, and no other deck"), and the `startDevServer --remote` tests in `tests/server/dev.test.ts` ("protects presenter with HTTP Basic and leaves the player open", "lets a phone in as the presenter once with a pairing code, then by cookie", "keeps the voice timeline and audio, made from the script, behind the password", "streams diagnostics to the presenter only, and reloads to everyone", "relays the presenter's laser to the room, and nobody else's", "a server scoped to one deck serves none of the project's other decks"), and "serves no asset behind an assets folder that links out of the project" in the same file.

**4. Other websites open in the user's browser** while the dev server runs, locally or with `--remote`.

- **Controls**: pages that can make the browser send a request to any address and port, and frame or embed what comes back.
- **dek guarantees**: the server answers only to a loopback Host (`127.0.0.1`, `localhost`, `[::1]`), and with `--remote` also to an IP address or this machine's own name, so a site cannot reach it under a name of its own (DNS rebinding). A request that is not a GET, or that asks for a WebSocket, must carry the server's own Origin or none, as `dekc goto` sends none; `null` is refused. No other site can move the deck, open a socket, or write marks or annotations.
- **dek guarantees, on what the browser does with an answer**: every answer dek writes, pages, files, listings, streams, and refusals alike (the guard's 400 and 403, the 401, a 404, the pairing's 303 and 403, a 500 from the error handler), carries `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, and `Content-Security-Policy: frame-ancestors 'self'`. Bun answers a few requests itself, before dek sees them, and without the headers: one its parser refuses (a malformed request line or HTTP/1.1 with no Host, 400; a `Content-Length` too large, 413; headers too large, 431) and a WebSocket upgrade of a version it does not take (426, from `server.upgrade`). None of those has a body a page could use. The browser then hands none of it to another origin's page, as a sound, a stylesheet, a picture, or a script, and shows none of it in another origin's frame. `frame-ancestors` goes on every answer, not only pages, because the voice or a listing opened in a frame is a page too: another site framed the voice's audio as readily as the presenter view. `same-origin`, not `same-site`: Chromium takes two ports of `localhost` for one site, and with `same-site` a page on another port of `localhost` played the voice and read the theme's token; `same-origin` keeps everything to the server itself. The deck's own pages are unaffected: they ask only their own origin, a slide's `<iframe>` of a file in its `assets/` is the same origin, a phone opens the server's own address, and a successful WebSocket upgrade has no answer of dek's to carry headers. Nothing in dek frames or embeds a dev page from another origin, and no guide suggests it; a page elsewhere that framed one now shows an error in its place.
- **What a plain GET could do before those headers**, from a run on 2026-10-27 with a page at `http://localhost:<port>/` against a server at `http://127.0.0.1:<port>/`, in headless Chromium from Playwright 1.64. A local server has no password, so every request is cleared for the presenter, and the page could: play the deck's voice audio and read its length with `<audio>`, given the click a browser's autoplay rules ask for; load the theme as a stylesheet and read its custom properties with `getComputedStyle`, though not its rules; tell whether a deck exists, since the theme route loaded or failed, and whether it had a voice; and frame the presenter view, notes and all, and the voice. With `--remote`, presenter routes answered 401 to the same page, also after the browser had paired, since a Lax cookie goes with no cross-site subresource or frame; but after the browser had signed in with Basic credentials, given in the address for the run, Chromium sent them with the cross-site requests, so the voice played and the framed presenter view read the annotations, marks, and event stream from inside the frame. With the headers, the same runs, local and signed in with Basic, got none of it: the audio and the theme failed for a deck that exists as for one that does not, no token came through, and every frame showed an error.
- **What a plain GET still does**: it reaches the server, which answers as it would its own page; the browser keeps the answer. No GET makes dek synthesize a voice or rebuild. The voice route serves what `dekc voice` cached, or 404; a GET renders a page, lists files, or opens an event stream, which is the deck's own work, and listing annotations may rewrite `.dek/annotations.json` to follow elements that moved, with nothing the request chose. In every run the page read no JSON or HTML, `EventSource` failed its CORS check, and the WebSocket and the POSTs were refused. A link from another site opens a page in the user's own tab, as any link does, with the Lax cookie as Lax means; the site cannot read it. Some browsers now ask before a public site reaches a loopback or LAN address; dek does not rely on it. The port is the operating system's choice unless `--port` names one.
- **Enforced in**: `src/server/auth.ts` (`requestGuard`, `servesHost`, `sameOrigin`), called first in `answer` in `src/server/dev.ts`; `keepToOwnOrigin` in `src/server/auth.ts`, through which `listen` in `src/server/dev.ts` passes every answer dek writes, from `fetch` and from the error handler alike.
- **Shown by**: `tests/server/auth.test.ts` ("serves a local server only under a loopback host name, against DNS rebinding", "serves --remote under an address or this machine's name, never another DNS name", "refuses a move or a socket from another origin", "allows the deck's own page, and dekc goto, which sends no Origin", "keepToOwnOrigin"), the "startDevServer response headers" tests in `tests/server/dev.test.ts`, one request per kind of answer, with "answers an unexpected failure with a bare 500 and logs it to stderr" for the error handler, and `tests/server/dev-browser.test.ts`, the run above in a real Chromium, from a page on another site, on another port of the server's address, and on another port of `localhost`, against a local server and against a `--remote` one the browser is signed in to with Playwright's `httpCredentials` ("another origin can neither play the voice, read the theme, tell decks apart, nor frame a page", "nor can it with --remote, in a browser signed in with the password", and "the deck's own pages still load the voice and the theme, and frame its views").

**5. The working directory**: the files of the project dekc runs in, as configuration of the Bun that runs dek ([ADR 12](0012-take-github-tokens-and-dek-variables-only-from-what-the-user-sets.md)).

- **Controls**: `.env` files, `bunfig.toml`, `tsconfig.json`, `package.json`, `node_modules` and its `.bin`, and links.
- **dek guarantees**, when dekc is started as its bin: no `.env` sets a variable and no `bunfig.toml` preloads code, in dek or in any bun it starts, which also gets `--no-install`. When Bun loaded `.env` files anyway, every `DEK_` variable and `NODE_TLS_REJECT_UNAUTHORIZED` they name is removed before dek reads any, with a warning. The package ships its own `tsconfig.json`, nearest dek's files, so a project's `paths` cannot redirect dek's imports. Playwright is found from dek's own install, and rumdl from `PATH` or beside dek's install, unless a `DEK_` variable names them; dek never looks in the working directory's `node_modules` for either. A token goes only to `https://api.github.com`, and only one the user set.
- **Enforced in**: the shebang of `src/cli.ts`, `src/cli/env-file.ts` (`dropEnvFileVariables`), `src/core/spawn.ts` (`BUN_FLAGS`, `workerCommand`), `src/core/slide-script-eval.ts` (the evaluator's command), the `files` of `package.json`, `src/core/playwright.ts` (`resolvePlaywrightModule`), `src/core/rumdl.ts` (`resolveRumdlBin`), `src/core/github.ts` (`authorization`).
- **Shown by**: `tests/cli/env-file.test.ts` (the bin's flags, a `.env`, a `bunfig.toml` preload), `tests/core/spawn.test.ts` ("runs a .ts worker with bun and anything else as is"), `tests/core/playwright.test.ts` ("resolvePlaywrightModule"), `tests/core/rumdl.test.ts` ("resolveRumdlBin"), `tests/core/github.test.ts` ("authentication"), and `scripts/check-package.sh`, which tries a project's `paths` against the packed tarball.

**6. Dependencies, and the tokens that publish** ([ADR 3](0003-release-through-release-please-and-npm-trusted-publishing.md), [ADR 19](0019-keep-dependency-code-away-from-the-tokens-that-publish.md)).

- **Controls**: the code of every package dek or its CI installs, and of every action CI runs.
- **dek guarantees**: no job that runs dependency code can mint the token npm publishes with. `pack` installs from the lockfile, checks the tarball, and uploads it, with no `id-token`; `publish` holds `id-token: write`, checks out and installs nothing, and publishes that tarball with `--ignore-scripts`. Pages' write permissions are `deploy`'s alone. Actions are pinned to commits, no checkout keeps its token, rumdl and adrs are checked against their SHA-256, and publint comes from the lockfile. In this repository, `bun install` takes no version published in the last seven days, and Dependabot waits as long, security updates aside.
- **Not covered**: zod, dek's one runtime dependency, is a caret range resolved when a user installs dek, with no wait; Playwright is the user's own install; a project `dekc init` writes gets no `bunfig.toml`.
- **Enforced in**: `.github/workflows/release.yml`, `pages.yml`, and `ci.yml`, `.github/dependabot.yml`, `bunfig.toml`, `scripts/check-package.sh`.
- **Shown by**: each release, whose `pack` job runs `scripts/check-package.sh`, and the Scorecard workflow. Nothing in `tests/` checks the workflows.

**7. Where Chromium's sandbox cannot start.** `launchChromium` asks for the sandbox and, when that launch fails for any reason, launches again without one and says nothing. In a container running as root, or wherever else the sandbox cannot start, a ref's slide scripts in `shot` run in a renderer with no sandbox, the network still off, and the user is not told. This is a known gap, for ADR 29 to decide. Enforced in `src/core/playwright.ts` (`launchChromium`); no test shows that the sandbox is on, or what happens without it.

**Out of scope**:

- The deck author against their own machine. Their slide scripts run in their own browser and in the builds they open, as any page they write does.
- `DEK011`, style or script inside the markup. It is a convention rule that keeps slides in the shape lint and agents expect, not a boundary: a deck's `slides/*.ts` run either way.
- A launch that skips the bin's flags, such as `bun ./node_modules/.bin/dekc`, a project's `package.json` scripts, anything it commits under `node_modules`, and a `node_modules/.bin/dekc` that `bunx dekc` would pick ([ADR 12](0012-take-github-tokens-and-dek-variables-only-from-what-the-user-sets.md), SECURITY.md). `bunx` also puts the working directory's `node_modules/.bin` first on `PATH`, so under it a `bun`, `rumdl`, or `ffmpeg` committed there is the one dek finds on `PATH`; that is the same committed `node_modules`.
- Other processes and users on the machine. A local dev server has no password: whatever can connect to `127.0.0.1` is cleared for the presenter, and a client that sends no Origin may POST.
- The network between devices under `--remote`. It is plain HTTP, so whoever can read the traffic can read the password and the cookie, as the presenting guide says.
- What the user's agent does with what it reads. dek marks a ref's output and keeps a ref's title to one line of AGENTS.md; it does not judge a ref's words, or an annotation's.
- A ref's license. dek warns when there is none and leaves the reading of one to the user ([ADR 17](0017-start-a-deck-from-a-ref-s-theme.md)).

**Open items**, found while writing this record and left for the changes that fix them:

1. **Chromium's sandbox falls back without a word** (part 7).
2. **A ref's names reach dek's own messages and hints without the limits AGENTS.md puts on its title.** For a deck the repository lacks, `dekc ref owner/repo/<deck>` hints the name of every `decks/<name>/script.md` folder in it, in any characters, line breaks included; a pack with two decks names both; Bun's syntax error for a ref's slide script can quote its source; and the error for a ref's broken slide script hints `dekc lint`, which dek prints as `dekc lint <deck>` with the ref's deck name, and which lints the user's own decks, never the ref. An agent reads a hint as what to do next.
3. **`terminalSafe` keeps every `ESC [ … m`**, so a ref's text can carry color codes too, such as the one that hides text from a person while an agent reading the bytes still sees it.
4. **`dekc show`'s text output does not say the deck is a ref**, which only `--json` carries, and its `--- <file>` lines are text a ref's files can hold as well.
5. **Lint evaluates the top-level code of a project's slide scripts under `node:vm`**, in a separate bun, which is not a sandbox: for a project the user did not write, it is weaker than Chromium's.
6. **No test shows** that Chromium's sandbox is on, or that the network is off for more than `navigator.onLine`.

## Consequences

A change that bears on what someone else can make dek do is argued against this record: it names the party, says which guarantee it keeps or changes, and points at the code and the test. A change that breaks a guarantee here supersedes this record, or the part of it, in the open. A fix that brings the code back in line with a guarantee here needs no record of its own; the open items add or change a guarantee, and say so where they land.

SECURITY.md and the architecture guide's "A project you did not write" stay the reader's account, shorter than this one.

The record has to move with the code. A new route needs its place in `ROUTE_EXPOSURE`, already enforced by the compiler; a new command that reads a ref, a new way for a ref's text to reach the agent, or a new place dek runs a slide script needs its line here.

**What was not chosen:**

- **A threat model in `docs/`.** The site is for people using dek, in two languages; this is the record that decisions cite, and SECURITY.md and the architecture guide already give users the short version.
- **Fixing the other open items here.** Each is a change with its own tests, and the sandbox has its own record; listing them keeps this one about what holds and what does not.
- **Running a project's own slide scripts in a sandbox everywhere.** A deck is presented in the user's browser, so its scripts run there whatever dek does; dek keeps them out of its own process and leaves the page to the browser.
- **`frame-ancestors` on HTML pages alone.** Another site framed the voice's audio as it framed the presenter view; a header on every answer costs nothing and leaves no type out.
- **`X-Frame-Options` beside it.** A browser that knows `frame-ancestors` ignores `X-Frame-Options` when both are sent, and every current one does; one header is one thing to keep right.
- **A password on a local server.** It would keep out other sites' requests, but at the price of a password on every local start, to guard against what the headers already stop; the processes it would also keep out run as the user (Out of scope).
