# プロジェクト構造

目標: プロジェクトとデッキの境界を把握し、どこで `dek` を叩けばよいかを決める。

## 単位

1 プロジェクト = N デッキ。デッキが 1 つでも `decks/` は必ずある。CLI も開発サーバも AI エージェントも、パス解決に分岐を持たない。

```
my-talks/                       # プロジェクト（dek init）
├── dek.toml                    # lint 閾値と字数/分
├── theme.css                   # 新しいデッキの出発点
├── AGENTS.md                   # AI 向け規約（sync が生成）
├── assets/                     # 素材の置き場。デッキへはコピーして使う
├── decks/
│   └── 2026-04-vite/           # デッキ（dek new）
│       ├── script.md           # 単一の真実
│       ├── theme.css           # このデッキのもの
│       ├── slides/
│       ├── assets/
│       ├── dist/               # dek build / pdf / video の成果物
│       │   └── 2026-04-vite.html
│       └── .cache/             # voice / video / shots の中間物
└── .dek/
    └── schema.json
```

プロジェクトはデッキを置く場所であって、デッキが依存する実行環境ではない。

## テーマは複製する

プロジェクト直下の `theme.css` は新しいデッキの出発点。`dek new` はこれをデッキの中へコピーする。

```bash
dek new 2026-09-dek
dek new 2026-09-dek --theme-from 2026-04-vite
```

共有参照にすると、9 月にテーマを磨いた結果として 4 月のデッキの描画が変わり、見出しが 1 行に収まらなくなり、lint が過去のデッキに対して警告を出しはじめる。終わったトークは終わった状態で固定する。物理的なコピーがいちばん確実だ。

今回の改良を次回の出発点にするときは `cp` する。専用コマンドは持たない。過去のデッキが、そのままテーマのライブラリになる。

```bash
cp decks/2026-09-dek/theme.css theme.css
```

`assets/` も同じ。プロジェクト直下は素材の置き場で、デッキは使うものを自分の `assets/` へコピーする。

声も同じ。`dek.toml` に `[voice]` があるときだけ、`dek new` は `voice/voice.toml` をデッキへコピーする。9 月に話者を変えても、4 月のデッキの声は変わらない。

## 実行場所がスコープを決める

`dek.toml` を上へ探索してプロジェクトルートを決める（Cargo workspace と同じ）。

| どこで実行したか | 対象 |
| --- | --- |
| プロジェクト直下 | 全デッキ |
| デッキの中 | そのデッキ |
| どこでも `<name>` または `--deck <name>` | 指定したデッキ |

プロジェクト外で `dek new` を叩くと `dek init` を促して終了する。
