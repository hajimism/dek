# エージェント向けの品質基準

dek はコーディングエージェントが使うことを前提に設計しています。このページでは、その使いやすさを測るための品質基準を定義します。機能変更で損なってはならない要件と、改善で高めていく指標の両方を定めており、コマンド・診断・規約の設計やレビュー時に参照します。

エージェントの作業は「プロジェクトの把握 → スライドの執筆 → 結果の確認 → 問題の修正 → 作者へ返す判断」のループです。以下の 8 つの基準は、このループのどこかで作業が詰まる典型的な原因に対応しています。

## 基準

### 1. 案内が正確である

`AGENTS.md` と `dekc help --agent` だけで作業を始められ、書かれている内容がプロジェクトの実態と一致していること。

- `AGENTS.md` に記載されたクラス・トークン・レイアウトが、デッキのテーマに実在する。
- 作成したばかりのプロジェクトにも、エージェントに必要な案内が一通りそろっている。
- レイアウトが想定する HTML 構造など、正しいマークアップを書くための情報にこの 2 つからたどり着ける。

### 2. 規約がすべて検査される

エージェント向けに定めた規約は、すべて lint ルールとして機械的に検査されること。lint を通ったデッキは、文書化された規約に違反していない。

lint の対象は「規約を守ろうとしているエージェントがうっかり犯すミス」であり、検査をすり抜けるために意図的に細工された入力は対象外です。たとえば `<iframe srcdoc>` に隠したスクリプトや `globalThis["Da" + "te"]` のような難読化は扱いません。dek がビルドするのは自分や自分のエージェントが書いたデッキであって、見知らぬ第三者のコードではありません。lint は規約チェッカーであり、セキュリティサンドボックスではありません。

- `AGENTS.md` の各規約が具体的なルール ID に対応している。
- 検査できない規約は、検査できる形へ書き直すか規約から外す。
- ルールの挙動（重要度を含む）がドキュメントの記述と一致している。

### 3. 描画結果を確認できる

人間が画面を目視しなくても、エージェント自身が描画結果を検証できること。

- はみ出しやコントラストのように数値・幾何で判定できる問題は、スクリーンショットの解釈に頼らず診断として返す。
- スクリーンショット、遷移途中のフレーム、現在表示中のスライドをコマンドで取得できる。
- 実行しなかった検査は「スキップ」と明示し、合格扱いにしない。

### 4. 診断から直し方がわかる

すべての診断が、問題の場所と次に取るべき行動を示していること。

- 場所が正確である（修正すべきファイルと、該当する場合は行番号・列番号）。
- `hint` は記載どおりにそのまま実行でき、その診断が出た状態から実行して成功する。
- `hint` が案内する先に、約束した情報が確かにある。
- 他のスライドに新たな問題を起こす修正を勧めない。

### 5. 結果を機械的に読める

エージェントが自然言語のメッセージをパースせずとも、次の行動を判断できること。

- 結果を返すコマンドはすべて `--json` に対応し、一貫した構造で返す。
- 各診断が重要度を持ち、終了コードは重要度だけで決まる。
- ピクセル数・コントラスト比・問題のある値などの数値は、メッセージ文中だけでなく構造化フィールドにも含める。

### 6. 止まりどころが明確である

測れる問題がもう残っていないことと、人間へ委ねるべき判断が何かを、少ない試行回数で見極められること。

`dekc lint --visual` の通過は完成デッキの必要条件であって十分条件ではありません。わかるのはルールで判定できる問題がないことだけで、スライドのバランス・話の筋・時間配分はコンタクトシートと台本を読んで判断し、最終的に作者が決めます。

- 作成直後のプロジェクト、追加直後のデッキ、同梱サンプルがそのままの状態で lint を通る。
- lint は検出できた問題を 1 回の実行ですべて報告し、1 件ずつ小出しにしない。
- `warning` は報告してもコマンドを失敗させない。「未完成」を意味するのは `error` だけとする。

### 7. 変更操作が安全である

ファイルを変更するコマンドは、エージェントが自然に到達しうるどの状態からでも動き、中途半端な状態を残さないこと。

- どのファイルを先に編集していてもコマンドが正しく動く。
- 失敗したコマンドはファイルを一切変更しない。
- 入力は受け取った時点で検証し、処理の途中で初めて失敗させない。

### 8. 出力の表記がそろっている

同じ種類の情報は、どのコマンドでも同じ表記で出力すること。

- ソースツリー内のパスは、すべての出力箇所で作業ディレクトリからの相対パスにする。ビルド結果やスクリーンショットなどの成果物は、そのまま開けるよう絶対パスにする。
- 日本語を含んでも表の列幅がずれない。
- エラーメッセージと `hint` で同じ文言を繰り返さない。

## 違反の重要度

変更や不具合が上の基準に反する場合は、エージェントの作業への影響度で重要度を決めます。

| 重要度 | エージェントへの影響 |
| --- | --- |
| S1 | 作業が止まる、または測れるはずの問題を「問題なし」と誤報告する |
| S2 | ゴールには到達できるが、実行回数や推測が増える |
| S3 | 表示上の体裁だけで、作業効率は落ちない |

あわせて、エージェントがその違反にどう遭遇するかも区別します。通常の作業フロー（ドキュメントどおりにスライドを書く、`hint` に従う、自然な順序でコマンドを打つなど）で踏むものは「自然」、抜け道を探すために仕立てた入力が要るものは「作為的」とします。

| | 自然 | 作為的 |
| --- | --- | --- |
| S1 | 新機能より優先して直す | 該当箇所に手を入れる際に直す |
| S2 | 新機能より優先して直す | 該当箇所に手を入れる際に直す |
| S3 | 余裕があるときに直す | 余裕があるときに直す |

難読化しないと踏めない作為的な違反は基準 2 の対象外として予定に入れずクローズします。
