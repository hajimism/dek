# チュートリアル

このチュートリアルでは、短いトークを 1 本、ゼロから作り上げます。題材は「バグだと思ったら設計の問題だった」という 10 分のライトニングトークです。終わるころには、ビート付きの台本、喋りに合わせて要素が現れる手書きスライド、2 枚をまたいで移動する図、規約の範囲内で変更したテーマ、そして USB メモリからそのまま発表できる HTML ファイルが手元にそろいます。

どのステップの終わりで手を止めても、そのまま発表できる状態になっています。dek は台本だけで成立するように設計されており、そこから先の工程はすべて必要に応じて足す仕上げです。

必要なのは [Bun](https://bun.sh) 1.4.3 以上だけです。声・動画・Playwright はここでは使いません。

## 1. プロジェクトを作る

```bash
bunx @hajimism/dek init lightning --deck postmortem
cd lightning/decks/postmortem
```

`init` は dek をプロジェクトにインストールし、最後にこの `cd` コマンドを表示します。以降、このページで `dekc` と書いてある部分は `bunx dekc`（プロジェクトに入れた dek）と読み替えてください。

## 2. 台本を書く

`script.md` の中身をトークの台本に置き換えます。実際に声に出すつもりで書いてください。スライドのレイアウトはまだ考えなくて構いません。

```markdown
---
# yaml-language-server: $schema=../../.dek/schema.json
title: バグだと思ったら設計だった
event: Lightning Talks
date: 2026-05-14
duration: 10m
---

## intro

先月、見つけるのに 3 日かかったバグを出しました。
なぜ 3 日かかったのかを話します。理由はコードではなかったからです。

> ゆっくり。最初の一文を落ち着かせる。

## 何が見えたか {#symptom}

ある地域のユーザーだけ、古い価格が見えていました。間違った価格ではなく、古い価格。
毎回 5 分遅れで、そこだけ。

## どこを見たか {#search}

当然の場所を、当然の順番で見ました。

### キャッシュ {#cache}

まずキャッシュ。問題なし。

### キュー {#queue}

次にキュー。これも問題なし。

### 時計 {#clock}

そして、あるホストの時計。5 分遅れていました。

## なぜ 3 日かかったか {#cause}

時計がバグでした。でも 3 日かかった理由は、
どのホストがそのリクエストを処理したのかを、システムのどこも教えてくれなかったことです。
それはバグではありません。設計です。

## 何を変えたか {#fix}

時計を先に直しませんでした。すべてのレスポンスに「どこから来たか」を書かせました。
時計はそのあと 10 分で直りました。

## 持ち帰ってほしいこと {#close}

バグが見つからないとき、システムが何を言わないでいるかを問いましょう。
```

押さえておきたいポイントが 3 つあります。

- `## intro` はそのまま id として有効なため `{#...}` を省けます。他の見出しには日本語が含まれるため、それぞれ `{#id}` を明示しています。id が HTML のファイル名になり、見出しの文言が観客と発表者ビューに表示されます。
- `## どこを見たか` の下にある `###` が **ビート** です。喋りを 3 つの区切りに分けます。この段階では画面に特別な動きは起きませんが、それで問題ありません。
- 引用（`>`）は自分用のト書きです。読み上げ対象にも所要時間の計算にも含まれず、観客にも見えません。

## 3. 開発サーバーを起動する

```bash
dekc
```

表示された URL をブラウザで開きます。スライドは全部で 6 枚です。すべて見出しから自動生成されており、1 枚目はデッキのタイトル、2 枚目以降は見出しの文言、`search` は 3 つのビートを並べた構成になっています。

右矢印キーを押してみてください。`search` では 3 つのビートが 1 つずつ現れてから、次のスライドへ進みます。`p` を押すと発表者ビューに切り替わり、現在のセクションの台本が表示され、いまのビートがハイライトされ、最初にスライドを送った時点から経過時間のタイマーが動き出します。

開発サーバーが生成した `slides/search.html` を開いてみましょう。

```html
<section class="slide" data-layout="default">
  <h2 class="slide-title">どこを見たか</h2>
  <ul>
    <li data-step="cache">キャッシュ</li>
    <li data-step="queue">キュー</li>
    <li data-step="clock">時計</li>
  </ul>
</section>
```

各項目が `data-step` でビートの id を参照しています。あるビートまで進むと、プレイヤーはそのビートとそれ以前のビートに紐づく要素すべてに「表示済み」の印を付けます。表示済みの要素をどう見せるかはテーマの役割です。

::: tip ここで止めてもいい
この時点で `dekc build` を実行すれば、もう発表できるデッキが手に入ります。ここから先は、台本の内容以上に画面で伝えたいことを作り込む作業です。
:::

## 4. 尺を確かめる

別のターミナルを開き、デッキのディレクトリで次を実行します。

```bash
dekc ls
```

`duration` で設定した持ち時間、字数から計算した見積もり時間、セクションごとの時間配分が表示されます。dek は CJK を 300 字/分、それ以外を 130 語/分で計算し、引用は数えません。このチュートリアルの台本は 1 分ほどで読み終わる分量なので、`dekc ls` の末尾に `1 diagnostic` と出ます。中身は `dekc lint` や開発サーバーでも表示される `DEK041` の警告（「10 分の持ち時間に対して短すぎる」）で、スライドを盛るのではなく台本を書き足すべき合図になります。警告なので lint 自体は通過します。声に出すつもりの言葉は、台本に書いて初めて尺に数えられます。

## 5. 1 枚を手で書く

`cause` はこのトークでいちばん大事なスライドです。ちゃんとしたレイアウトに変えましょう。`slides/cause.html` を開き、骨格を次の内容で置き換えます。

```html
<section class="slide" data-layout="two-col">
  <h2 class="slide-title">時計がバグで、沈黙が設計だった。</h2>
  <div class="col">
    <p class="node">cache</p>
    <p class="node">queue</p>
    <p class="node node-parent">clock: −5 min</p>
  </div>
  <div class="col">
    <p class="node">response</p>
    <p class="node node-parent">served-by: ???</p>
  </div>
</section>
```

保存すると、ブラウザはこのスライドだけを即座に差し替えます。ここで使った `slide-title`・`col`・`node`・`node-parent` はすべて同梱テーマで定義されているクラスです。試しにテーマにないクラス（たとえば `class="node highlight"`）を足して保存してみてください。ターミナルとブラウザのオーバーレイの両方に、`theme.css` にそのクラスがないという `DEK010` のエラーが出ます。消せばエラーも消えます。

「書く → 保存する → 診断を読む → 直す」が基本のループです。開発サーバーは保存のたびに lint を走らせるため、診断が 0 件なら機械的に検出できる問題は残っていません。

## 6. 喋りに合わせて現す

いまの `cause` にはビートがないため、左右のカラムが同時に表示されます。「システムのどこも教えてくれなかった」と喋るタイミングで右カラムが出るよう、台本にビートを追加します。

`script.md` の `cause` セクションを次のように書き換えます。

```markdown
## なぜ 3 日かかったか {#cause}

時計がバグでした。でも 3 日かかった理由は、別のところにあります。

### システムが知っていたこと {#knew}

キャッシュは問題なし、キューも問題なし、ひとつの時計が遅い。それは知っていました。

### システムが言わなかったこと {#silent}

でも、どのホストがそのリクエストを処理したのかは、どこも教えてくれなかった。
それはバグではありません。設計です。
```

続いて `slides/cause.html` で、各カラムをビートに紐づけます。

```html
<section class="slide" data-layout="two-col">
  <h2 class="slide-title">時計がバグで、沈黙が設計だった。</h2>
  <div class="col" data-step="knew">
    <p class="node">cache</p>
    <p class="node">queue</p>
    <p class="node node-parent">clock: −5 min</p>
  </div>
  <div class="col" data-step="silent">
    <p class="node">response</p>
    <p class="node node-parent">served-by: ???</p>
  </div>
</section>
```

ブラウザでこのスライドを送ってみてください。最初のビートで左カラム、次のビートで右カラムが現れます。*いつ* 出すかは台本が決め、*どう* 見せるかはテーマが決めます。同梱テーマは要素を `display: none` ではなく `opacity` とわずかな移動で隠すため、ビートが進んでもレイアウトがガタつきません。

ビートを番号ではなく id で指定したことで、後から途中にビートを挿入しても紐づけがずれません。`dekc sync` が生成する骨格も同じ id を使うため、HTML を書き始める前にビートへ `{#id}` を付けておくと後が楽になります。

## 7. 図を次のスライドへ引き継ぐ

次の `fix` スライドでは、`cause` にあった `served-by` のノードを引き継いで答えに書き換えたいところです。両方のスライドで同じ `data-morph` 名を付けておくと、遷移時にブラウザが位置とサイズを滑らかに補間してくれます。

`slides/cause.html` の最後のノードに `data-morph` を付けます。

```html
<p class="node node-parent" data-morph="served-by">served-by: ???</p>
```

`slides/fix.html` を次のように書き換えます。

```html
<section class="slide" data-layout="default">
  <h2 class="slide-title">すべてのレスポンスに出自を書かせる</h2>
  <p class="node node-parent" data-morph="served-by">served-by: host-07</p>
  <p class="node">そのあとで時計を直す。10 分。</p>
</section>
```

`cause` から `fix` へ送ってみてください。`served-by` の箱が消えて再登場するのではなく、右カラムから新しい位置へ滑らかに移動します。アニメーションのコードは一行も書いていません。`data-morph` が `view-transition-name` に変換され、残りはブラウザの View Transitions API が処理します。

Playwright を入れていれば、遷移の途中を静止画で止めて動きを確かめられます。

```bash
dekc shot cause --to fix --at 0.5
```

## 8. 規約の内側で見た目を変える

既定のテーマは暗い配色です。このデッキは暖色に変えてみましょう。デッキ内にある `theme.css`（プロジェクト直下のものではありません）を開き、`.slide` ブロックのトークンを 3 つ書き換えます。

```css
.slide {
  --fg: #2b1d12;
  --bg: #f6efe6;
  --accent: #b5471f;
  /* 他のトークンはそのまま */
}
```

保存すると、全スライドが新しい配色で描き直されます。ファイルの他の箇所に触れずに済んだのは、テーマ内の色がすべて `var(--fg)` や `var(--accent)` で書かれているからです。

ここで試しに規約を破ってみましょう。CSS ルールに生のカラーコードを直接書きます。

```css
.slide .node-parent {
  border-color: #ff0000;
}
```

保存すると lint が `DEK014`（トークン定義の外に生の値がある）を報告します。生の色・フォント名・絶対単位を書けるのは `--*` カスタムプロパティへの代入時だけで、それ以外の場所ではすべて `var()` を経由します。`var(--accent)` に戻せばエラーは消えます。

ここで編集した `theme.css` はこのデッキ専用のコピーなので、プロジェクト直下の `theme.css` や他のデッキには一切影響しません。仕上がりが気に入ったら、プロジェクト直下へコピーしてテンプレートに昇格させます。

```bash
cp theme.css ../../theme.css
```

これで、次に `dekc new` で作るデッキも暖色の配色から始まります。

## 9. 発表用ファイルをビルドする

```bash
dekc build
```

`dist/postmortem.html` が生成されます。全スライド、テーマ、プレイヤーのランタイム、画像がすべて minify された 1 ファイルにまとまっています。ブラウザで開き、矢印キーでビートとスライドを進めてみてください。`p` で発表者ビューが開き、同じファイルを別ウィンドウでも開くと `BroadcastChannel` で 2 つの画面が同期します。観客ビューをプロジェクターに、発表者ビューを手元のノート PC に出せば、サーバーもネットワークも不要です。

この 1 ファイルを USB メモリに入れて持っていくだけで発表できます。
