# プロジェクトとデッキ

**プロジェクト**は複数の**デッキ**をまとめて管理する場所です。このページでは、プロジェクトとデッキの境界、テーマを共有ではなくコピーする理由、コマンドの対象デッキが決まる仕組みを説明します。

## 1 プロジェクト、N デッキ

```
my-talks/                       # プロジェクト（dekc init）
├── dek.toml                    # 新しいデッキの初期値：クラス数上限、話速、音声設定
├── .gitignore                  # dist/ .cache/ .dek/server.json refs/
├── .rumdl.toml                 # script.md 用の Markdown ルール
├── theme.css                   # 新しいデッキの出発点になるテンプレート
├── AGENTS.md                   # エージェント向け規約（dek が更新するのは印の付いたブロックだけ）
├── tsconfig.json               # スライドスクリプト用のエディタ設定（dekc init が生成）
├── assets/                     # 共通の素材置き場。各デッキは使うものをコピーする
├── refs/                       # 見本として読む他人のデッキ。dek.toml の [refs] から取得する
├── packs/                      # ファイルで受け取ったデッキ。コミットする。refs/ はここから展開する
├── decks/
│   └── 2026-04-vite/           # デッキ（dekc new）
│       ├── script.md           # 順序・喋り・尺の元になる台本
│       ├── theme.css           # このデッキ専用のコピー
│       ├── slides/             # セクションごとに 1 HTML。任意で .css / .ts
│       ├── assets/             # スライドが参照するすべての素材
│       ├── dist/               # build / pdf / video の成果物
│       └── .cache/             # スクリーンショット・音声・動画の中間ファイル
└── .dek/
    ├── schema.json             # frontmatter スキーマ。sync のたびに再生成
    ├── slide.d.ts              # DekSlide の型定義。sync のたびに再生成
    └── renames.json            # dekc mv が記録する改名履歴。dek.pub 用にコミットする
```

デッキが 1 つだけでも `decks/` ディレクトリは必ず置きます。これにより、CLI・開発サーバー・エージェントのどれもが、どのプロジェクトでも同じルールでパスを解決できます。

各デッキは自己完結しています。`decks/2026-04-vite/` の中身は、デッキの外を一切参照しません。プロジェクトはデッキを置いておく場所であって、デッキが依存する実行環境ではありません。ディレクトリごとコピーしても、zip にして渡しても、何年か後に開いても、同じように描画されます。

## テーマは共有せず、コピーする

プロジェクト直下の `theme.css` はテンプレートです。`dekc new` を実行すると新しいデッキへコピーされ、以降は各デッキが自分のコピーを所有します。

```bash
dekc new 2026-09-dek
dekc new 2026-09-dek --theme-from 2026-04-vite
```

もしテーマを全デッキで共有していたら、9 月にテーマを調整した影響で 4 月のデッキの描画まで変わってしまいます。1 行に収まっていた見出しが折り返され、5 か月前に終えたトークに対して lint が警告を出しはじめるかもしれません。終わったトークは当時の見た目のまま固定されているべきで、それを最も確実に保証するのが物理的なコピーです。

デッキ内で育てたテーマを今後も使いたいと思ったら、`cp` でプロジェクト直下へ昇格させます。専用のコマンドはありません。

```bash
cp decks/2026-09-dek/theme.css theme.css
```

こうして過去のデッキそのものが、保守の要らないテーマライブラリになります。

`assets/` や音声設定も同じ考え方です。プロジェクト直下の `assets/` は素材置き場であり、各デッキは使うファイルだけを自分の `assets/` へコピーします。`dek.toml` に `[voice]` テーブルがあれば、`dekc new` がそれを `voice/voice.toml` として新しいデッキへコピーするため、9 月に話者を変えても 4 月のナレーションは変わりません。`dek.toml` の `max_classes` や話速の設定も同様に新しいデッキの frontmatter へコピーされるため、9 月に `max_classes` を厳しくしても 4 月のデッキがエラーになることはありません。

## 他人のデッキは読むだけで、借りない

見本にしたいデッキは、自分のものでも他人のものでも ref として登録できます。`dekc ref hajimism/dek/why-dek` を実行すると、`dek.toml` の `[refs]` にコミットが固定され、`refs/` に実体がダウンロードされます。中身は元のプロジェクトと同じ構成です。

```bash
dekc ref hajimism/dek/why-dek
dekc show hajimism/dek/why-dek timing
```

ref は読み取り専用です。`ls`・`show`・`theme`・`shot` で参照できますが、書き換えるコマンドはありません。スライドを参考にしたいときは、必要な部分を自分のデッキへコピーして自分のテーマで書き直します。スタイルガイドとして作られた ref のレイアウトをそのまま土台にしたい場合は、その ref のテーマで新しいデッキを始めます。

```bash
dekc new 2026-11-steerco --theme-from hajimism/dek/why-dek
```

新しいデッキには ref の `theme.css` のコピーだけが入り、先頭行に元の ref 名とコミットがコメントとして記されます。自分のデッキが ref を直接参照することはないため、自己完結性は保たれます。

ref の実体はコミットのキャッシュにすぎず、正体は `dek.toml` の固定情報です。そのため `refs/` は gitignore されます。削除しても別の環境へ clone しても何も失われず、次に参照したタイミングで固定コミットが再取得されます。また、自分のデッキを lint やビルドするときに dek が `refs/` を読み込むことはありません。

別組織の非公開リポジトリにあるデッキや、どのリポジトリにも属さないデッキなど、GitHub から取得できないものは pack ファイルで受け渡します。作者が `dekc pack` で書き出したファイルを、受け手が `dekc ref` で固定すると `file/<deck>` として読めるようになります。

```bash
dekc pack 2026-10-talk                 # 作者: decks/2026-10-talk/dist/2026-10-talk.tgz を作成
dekc ref ~/Downloads/2026-10-talk.tgz  # 受け手: file/2026-10-talk を固定し、packs/2026-10-talk.tgz に保存
dekc show file/2026-10-talk intro
```

pack には取り直せるリモートコミットがないため、`dekc ref` は pack ファイルを `packs/<deck>.tgz` に保存し、中身のファイルのダイジェストで固定します。`packs/` は `dek.toml` と一緒にコミットしてください。別環境で clone した際は、そこから `refs/` を展開します。他人のデッキが自分のリポジトリに含まれることになるため、作者の了解なく公開リポジトリへ置かないよう注意してください。

受け手がどこまで再利用できるかは pack に含まれる `LICENSE` で決まります。`dekc init` で作ったプロジェクトには `dek.toml` に `[pack] license = "CC0-1.0"` が入っているため、pack したデッキは CC0 1.0 で渡されます。テンプレートとして自由に再利用でき、それをもとに作ったデッキへ出典を書く必要もありません。出典表示を求める場合は `"CC-BY-4.0"` に変更し、ライセンスを付けずに渡す場合は該当行を消してください。

## 実行場所がスコープを決める

dek はカレントディレクトリから親方向へ `dek.toml` を探してプロジェクトルートを特定します。Cargo がワークスペースを見つけるのと同じ仕組みです。

| 実行した場所 | 対象 |
| --- | --- |
| プロジェクト直下 | 全デッキ |
| デッキの中 | そのデッキ |
| どこからでも（デッキ名か `--deck <name>` を指定） | 指定したデッキ |

プロジェクト直下で実行した `dekc lint` は全デッキを検証し、`dekc build` は全デッキをビルドします。`dekc show intro` のように対象を 1 つに絞る必要があるコマンドは、デッキ名の指定を求めます。デッキ名は位置引数でも渡せます（例：`dekc show 2026-04-vite intro`、`dekc lint 2026-04-vite`、`dekc 2026-04-vite`）。

プロジェクトの外で `dekc new` を実行すると、`dekc init` を案内して終了します。`refs/` の中でコマンドを実行した場合も止まり、自分のプロジェクトへ戻るよう案内します。
